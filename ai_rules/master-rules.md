# AGENTS.md

核心行為準則是「謹慎優先於速度」。減少 LLM 常見的過度工程、幻覺改動及程式碼污染。

## 1. 思考先行 (Think Before Coding)
拒絕假設，拒絕含糊。在動手前先明確邊界。
- 明確假設： 在實作前，口頭陳述你的假設。如果有任何不確定，必須詢問。
- 呈現選擇： 如果存在多種解釋，請列出選項並說明利弊，不要擅自決定。
- 推動簡單化： 如果有更簡單的方案，請主動提出並說服用戶。
- 引發衝突： 當需求與現有架構衝突時，停止操作並指出矛盾點。
- 技能觸發： 在開始任何任務前，優先調用 `@brainstorming` 進行設計驗證。

## 2. 極簡主義與鋼鐵法則 (Simplicity & Iron Laws)
只用最簡潔的方式解決問題，不要過度開發。
測試失敗時，才允許增加程式碼。絕不為未來設計。
- 無需求，不程式： 嚴禁添加未經請求的功能、抽象層或「靈活性」。
- 嚴禁過度配置： 除非測試要求，否則禁止引入 `ctx`, `logger`, `metrics`, `tracing`, `options={}`, `metadata={}`。
- 類型約束： 絕對禁止使用 `any`, `interface{}`, `object` 等模糊類型，除非測試證明其必要。
- 魔術字串： 禁止硬編碼數字或字串，必須提取為具名常量。
- 重寫限制： 除非明確指定，否則絕對禁止重寫整個文件。
- 不要過度測試：不需要測試不可能發生的情境。
- 可簡化就簡化：如果這段200行的程式碼能縮減到50行，請重寫。

自我檢查： 「資深工程師是否會說你寫的太複雜？是，則重寫。」

## 3. 外科手術式改動 (Surgical Changes)
只能動到必須動的地方。只能清理由你自己寫的程式。
- 禁止「順便」優化： 不要修復鄰近的程式碼格式、註釋或無關邏輯。
- 尊重既有風格： 即使你認為現有風格不佳，也必須保持一致。
- 孤兒處理： 僅刪除因「你的改動」而失效的 Import 或變數。
- 追蹤準則： Diff 中的每一行改動，都必須能直接溯源至用戶的原始請求。

## 4. 目標驅動與 TDD 循環 (Goal-Driven & TDD)
將任務轉化為可驗證的目標。循環直到通過。
1. 寫下計畫： 將工作拆解為 2-5 分鐘的微小任務，標註檔案路徑與驗證步驟。
2. RED（失敗測試）： 優先編寫一個失敗的測試案例，並確保它確實失敗。
3. GREEN（最小實作）： 編寫能讓測試通過的最少程式碼。嚴禁添加額外欄位或依賴。
4. REFACTOR（重構）： 僅在測試通過後進行清理，且不得引入新行為。

## 5. 特定語言禁忌 (Forbidden Patterns)
| 語言 | ❌ 絕對禁止 (除非測試要求) | ✅ 推薦做法 |
| : | : | : |
| Go | `func(ctx, logger, metrics)` | `func(amount int) error` |
| TS | `async function(options: any)` | `async function(id: string)` |
| Python | `def process(ctx, kwargs)` | `def process(user_id: str)` |

## 6. 上下文完整性校驗 (Safeguards)
在標記任務完成前，必須強制執行以下檢查：
- 變數完整性： 計畫中提到的所有變數是否都已定義、初始化並使用？
- 跨文件依賴： 修改了函數簽名後，是否已同步更新所有調用點？
- 範圍限制： 檢查 Git Diff，是否包含任何非請求的格式化或無關改動？
- 禁止 swallow 錯誤： 確保所有 error 都被顯式處理或傳遞，嚴禁靜默忽略。

## 7. 故障排除模式
如果卡住，請按此順序操作：
1. 碰撞思考： 強制連結不相關的概念以尋找靈感。
2. 反轉假設： 翻轉現有約束，確認是否為偽命題。
3. 簡化級聯： 尋找一個能同時消除多個複雜組件的洞察點。

當 Diff 中的無關變動變少、提問次數增加、程式碼更短時，這套指南即視為運作良好。
